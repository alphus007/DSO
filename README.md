# DevSecOps WordPress Lab 🔐

> Automated Vulnerability Discovery & Remediation Pipeline  
> **Stack:** Docker · WordPress · WPScan · GitHub Actions · GHCR · Docker Hub

---

## Overview

This repository implements a full DevSecOps pipeline for a containerised WordPress deployment:

1. **Deploy** a WordPress environment via `docker-compose`
2. **Scan** automatically using WPScan inside GitHub Actions
3. **Analyse** vulnerabilities and assess exploitation paths
4. **Patch** WordPress core, PHP version, and OS packages
5. **Harden** the image (non-root user, PHP config, Apache headers, WP settings)
6. **Rebuild & push** the fixed image to GHCR and Docker Hub
7. **Verify** by re-scanning the hardened image in the same pipeline

```bash
# 2. Copy and edit env file
cp wp-config-placeholder.txt .env

# 4. Run WPScan manually
docker run -it --rm wpscanteam/wpscan \
  --url http://localhost:8080 \
  --enumerate u,vp,vt \
  --force
```

## GitHub Actions Pipeline

The pipeline (`scan.yml`) runs in **three sequential jobs**:

| Job | Purpose |
|-----|---------|
| `initial-scan` | Deploys vanilla WordPress → runs WPScan → saves artefacts |
| `build-hardened-image` | Builds Dockerfile.hardened → pushes to GHCR & Docker Hub |
| `verification-scan` | Deploys hardened image → re-scans → compares before/after |

### Required GitHub Secrets

| Secret | Description |
|--------|-------------|
| `WPSCAN_API_TOKEN` | WPScan API token (get one free at wpscan.com) |
| `DOCKERHUB_USERNAME` | Your Docker Hub username |
| `DOCKERHUB_TOKEN` | Docker Hub access token |

> `GITHUB_TOKEN` is auto-provisioned – no action needed.

## Hardening Measures

### Infrastructure
- Multi-stage Docker build (builder ≠ runtime)
- Base image: `wordpress:6.5-php8.3-apache` (latest stable)
- OS packages updated at build time
- Unnecessary packages removed (`wget`, `netcat`, `telnet`)
- SUID/SGID bits stripped from non-essential binaries
- Container runs as `www-data` (non-root)
- `no-new-privileges` security option set

### PHP
- `expose_php = Off` (hides version from headers)
- `display_errors = Off`
- `disable_functions` blocks dangerous built-ins (`exec`, `shell_exec`, `system`, …)
- Secure session cookie flags

### Apache
- `ServerTokens Prod` / `ServerSignature Off`
- `X-Frame-Options: DENY`
- `X-Content-Type-Options: nosniff`
- `X-XSS-Protection: 1; mode=block`
- `Referrer-Policy: strict-origin-when-cross-origin`

### WordPress Application
- `DISALLOW_FILE_EDIT` / `DISALLOW_FILE_MODS`
- XML-RPC fully disabled
- User enumeration via REST API blocked
- WP version stripped from HTML `<meta>`
- `readme.html`, `license.txt`, `wp-config-sample.php` removed
- `wp-config.php` permissions set to `440`
- Randomised table prefix
- Debug mode disabled
- Core minor updates set to auto-apply

## DevSecOps Shift-Left Strategy

This pipeline embodies **shift-left security** by:

- Running vulnerability scans on every `push` to `main` — not just at release
- Failing the pipeline if the hardened image has *more* vulnerabilities than baseline
- Storing scan artefacts as GitHub artefacts and committing them to the repo for audit
- Enforcing hardening at **image build time** (not as a post-deployment script)
- Using `docker/metadata-action` to tag images with SHA and branch — enabling traceability
